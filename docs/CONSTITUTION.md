# Конституция документации и разработки

| Поле | Значение |
| --- | --- |
| Статус | `approved` |
| Владелец решения | пользователь проекта |
| Последняя проверка | 2026-08-06 |
| Область ответственности | правила hybrid SDD, качества и изменения канона |
| Supersedes | нет |
| Approval | пользователь проекта / 2026-08-05 / Stage 0; 2026-08-06 / anti-bloat amendment / approved |

## 1. Назначение

Документация должна позволять независимо ответить на пять вопросов:

1. какую проблему, для кого и ради какой ценности решает проект;
2. какое наблюдаемое поведение обязательно и как оно проверяется;
3. откуда взяты внешние факты и как получены производные расчёты;
4. почему выбраны конкретные UX- и архитектурные решения;
5. какими доказательствами подтверждаются AI workflow, работающий результат и конкурсное демо.

Документация не является пересказом кода. Код, прототип и LLM-переписка не могут молча заменить отсутствующее решение. Расхождение между approved-спецификацией и реализацией считается дефектом, который разрешается явно.

## 2. Базовый процесс

Проект разрабатывается через адаптированный spec-driven development:

```text
explore
  -> proposal
  -> requirements and scenarios
  -> clarification
  -> design and ADR
  -> contracts and acceptance/eval checklist
  -> tasks
  -> cross-artifact analysis
  -> user approval
  -> implementation
  -> verification
  -> canonical-spec update
  -> change archive
```

Для всего проекта сначала создаётся `spec of specs`: система разделяется на независимо проверяемые вертикальные срезы и подсистемы. Каждый срез проходит собственный цикл. Один общий мегадокумент не заменяет набор ограниченных спецификаций.

Процесс объединяет:

- [GitHub Spec Kit](https://github.github.com/spec-kit/reference/agentic-sdd.html) — quality gates и анализ согласованности;
- [Kiro Specs](https://kiro.dev/docs/specs/) — разделение requirements, design и tasks и проверяемые сценарии;
- [OpenSpec](https://github.com/Fission-AI/OpenSpec) — небольшие change-пакеты и последующая консолидация.

Эти инструменты не являются зависимостями проекта. Нормативны правила этого документа.

## 3. Скорость и атомарность

Один документ имеет одну основную ответственность. Requirements описывают поведение, design — способ реализации, contracts — границы взаимодействия, tasks — порядок работы, evals — способ измерения качества. Смешивать эти уровни нельзя.

Обычный документ должен быть короче 250 строк. После 250 строк он проверяется на разделение. Документ длиннее 400 строк допускается только как сгенерированный индекс, справочник или матрица с явным обоснованием в metadata.

Полный baseline всего проекта не блокирует полезный вертикальный срез. Срез можно реализовывать,
когда утверждены его требования, дизайн, контракты, acceptance/eval criteria и зависимости. Нельзя
использовать это правило для обхода нерешённого продуктового или безопасностного gate.

Каждый канонический документ содержит статус, владельца решения, дату проверки, область
ответственности и ссылки на заменяемые документы.

Сложность пропорциональна подтверждённой потребности. Новый артефакт должен либо обслуживать
approved requirement или canonical demo, либо уменьшать названный реалистичный риск или
неоднозначность. Пустые документы, универсальные framework-слои и abstractions для
гипотетического будущего запрещены.

Ошибка исправляется в компоненте — владельце нарушенного инварианта. Постоянный параллельный
pipeline, дублирующий формат или обходная подсистема требуют отдельного ADR и approval. Редкий
неопасный случай может завершаться явным unsupported result.

## 4. Статусы

Документы проходят состояния:

```text
draft -> review -> approved -> superseded
                         \-> archived
```

- `draft` — рабочая версия без обещания полноты;
- `review` — автор считает текст целостным и передал точную редакцию на проверку;
- `approved` — точную версию подтвердил пользователь;
- `superseded` — решение заменено с явной ссылкой на преемника;
- `archived` — документ сохранён как история и не участвует в текущем каноне.

Готовность реализации отделена от статуса документов:

```text
designed
component-implemented
integrated-e2e
source-verified
demo-verified
```

Слова «готово» и «реализовано» не используются без конкретного уровня и ссылки на evidence.

## 5. Нормативный язык и идентификаторы

`MUST`, `MUST NOT`, `SHOULD`, `SHOULD NOT`, `MAY` и их русские эквиваленты «обязан»,
«запрещено», «следует» и «может» используются только для проверяемых правил.

| Префикс | Смысл |
| --- | --- |
| `GOAL-*` | продуктовая или конкурсная цель |
| `REQ-*` | функциональное требование |
| `SCN-*` | пользовательский или системный сценарий |
| `INV-*` | доменный инвариант |
| `NFR-*` | нефункциональное требование |
| `PORT-*` | внешний или межмодульный порт |
| `ADR-*` | архитектурное или существенное UX-решение |
| `SRC-*` | политика или адаптер внешнего источника |
| `EVAL-*` | проверка качества продукта или AI workflow |
| `TEST-*` | детерминированная проверка реализации |

Идентификатор не переиспользуется с новым смыслом. Удалённый пункт остаётся в истории со статусом
и причиной изменения.

## 6. Требования и сценарии

Каждое `REQ-*` должно:

- описывать наблюдаемое поведение, а не имя будущего класса или файла;
- быть связано хотя бы с одним `GOAL-*` и `SCN-*`;
- иметь проверяемый acceptance criterion;
- указывать область действия и явные исключения;
- различать подтверждённый факт, пользовательское допущение и продуктовую гипотезу.

Сценарий фиксирует начальные условия, событие, ожидаемый результат и значимые побочные эффекты. Для
критического поведения обязательны happy path, negative path и recovery path.

Discovery содержит направления visual-first, Life Git, Evidence Passport и official-only внешние
данные. Их точная семантика, границы и статус решаются в Product Charter и requirements; до этого
они не являются нормативными требованиями этой конституции.

## 7. AI и evidence discipline

Каждый AI workflow явно описывает:

```text
Input -> Process -> Evals -> Output
```

Функция, сводящаяся к одному непрозрачному промпту без воспроизводимого процесса и evals, не
считается специфицированной.

LLM не является первичным источником внешнего факта и не доказывает собственный результат.
Спецификация должна разделять пользовательские факты, официальные внешние факты, производные
расчёты, допущения, иллюстрации и неизвестные значения. Точные runtime-правила повторной проверки,
снапшотов, конфликтов и недоступных источников определяются отдельными requirements и contracts.

Производный результат должен быть воспроизводим по входам, формуле или алгоритму и версиям
использованного evidence. Текстовая убедительность не заменяет такую трассировку.

## 8. Решения и supersession

Нетривиальное решение оформляется как ADR. ADR содержит контекст, варианты, решение, последствия и
ссылки на поддерживаемые требования.

Decision status проходит `proposed -> accepted -> superseded`; отклонённый вариант получает
`rejected`. Это отдельный статус от lifecycle Markdown-документа.

Новое решение не переписывает старую мотивацию. Оно получает новый ADR и ссылку `supersedes`.
Действующее правило должно находиться без хронологического расследования.

## 9. Change-пакеты

Существенное изменение создаётся в `docs/changes/active/<change-id>/`:

```text
proposal.md       why, scope and non-goals
requirements.md   changed behavior and scenarios
design.md         UX/technical decisions and boundaries
tasks.md          ordered implementation work
validation.md     traceability and fresh verification evidence
```

Для малого изменения файлы можно объединить, если сохранены те же разделы и gates. После
реализации и проверки изменение переносится в канонические документы, а пакет архивируется.

Опечатка или docs-only правка, не меняющая поведение, контракт, evidence policy или данные, может
вноситься напрямую с проверкой. Low-risk change может быть одним файлом с нужными секциями и одним
совмещённым approval; пустые артефакты ради процесса запрещены.

## 10. Traceability и cross-artifact analysis

Для реализуемого поведения существует цепочка:

```text
GOAL -> REQ -> SCN -> INV/ADR -> CONTRACT -> TEST/EVAL -> EVIDENCE
```

Перед реализацией проверяется:

- нет ли требования без сценария и acceptance criterion;
- нет ли design-решения, противоречащего требованию;
- нет ли внешнего факта без допустимого provenance;
- нет ли контракта без producer или consumer;
- нет ли задачи без требования или требования, потерянного в tasks;
- покрыты ли ошибки, recovery, privacy и деградация;
- можно ли показать результат в каноническом 3–5-минутном демо.

Неполная цепочка допускается только как явное ограничение с владельцем решения.

## 11. Проверка и доказательства

Документ не доказывает собственное утверждение. Уровни подтверждаются разными evidence:

- design review подтверждает `designed`;
- unit/domain tests подтверждают `component-implemented`;
- contract и black-box tests подтверждают `integrated-e2e`;
- повторная проверка официальных источников и расчётов подтверждает `source-verified`;
- воспроизводимый конкурсный сценарий и запись демо подтверждают `demo-verified`.

Проверка пропорциональна риску. Для среза обязательны happy path и только те negative или recovery
классы, которые реалистично способны нарушить approved invariant, правдивость, целостность данных
или canonical demo. Одного репрезентативного сценария на класс отказа достаточно, пока evidence не
показывает различающееся поведение. Процент покрытия и комбинаторный перебор профилей, стран,
источников и ошибок не являются самостоятельными целями.

## 12. Review gates

Подтверждение пользователя обязательно:

1. для этой конституции и её изменений;
2. для Product Charter, MVP и явных не-целей;
3. для baseline requirements и ключевых сценариев;
4. для семантики главных визуализаций и канонического demo story;
5. для архитектурных границ и ADR с существенными компромиссами;
6. для acceptance/eval checklist перед реализацией среза;
7. для финального documentation baseline и конкурсной версии.

Approval фиксируется в документе или `validation.md`: кто подтвердил, когда, какой scope и какое
решение. Подтверждение направления не считается подтверждением ещё не показанной точной редакции.

Проверяющий не должен молча исправлять принятое решение. Замечание либо исправляется автором,
либо становится явным решением пользователя.

## 13. Изменение конституции

Изменение начинается с proposal, описывающего причину, затронутые правила и миграцию существующих
документов. После подтверждения обновляются конституция, карта документов, шаблоны и проверки.
Прежняя версия сохраняется в истории.
