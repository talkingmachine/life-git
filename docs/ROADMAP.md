# Roadmap спецификации проекта

| Поле | Значение |
| --- | --- |
| Статус | `approved` |
| Владелец решения | пользователь проекта |
| Последняя проверка | 2026-08-06 |
| Область ответственности | путь от discovery к проверяемым вертикальным срезам |
| Supersedes | нет |
| Approval | пользователь проекта / 2026-08-06 / Stage 1 and Stage 2 baselines / approved |

Roadmap описывает подготовку канонических спецификаций и gates, а не календарный план разработки.
Для конкурсного pet-проекта используется сокращённый baseline: обязательная строгость сохраняется,
но документы создаются только тогда, когда уменьшают риск или делают демо проверяемым.

Выходы: [`architecture/spec-of-specs.md`](architecture/spec-of-specs.md) и
[`decisions/ADR-001-modular-monolith.md`](decisions/ADR-001-modular-monolith.md).

Exit gate выполнен 2026-08-06: пользователь подтвердил demo-spine из пяти срезов, walking skeleton
с минимальным Life Git, cross-slice ownership и acceptance intent. Scope `VS-1` требует
real-source end-to-end path без фиктивных внешних фактов; фактическое выполнение проверяется после
реализации, а не считается доказанным этим документом.

Stages 3–8 применяются к каждому вертикальному срезу только в затронутой части. Неприменимый stage
помечается `not applicable` с причиной, без пустого документа. Первый срез не обязан ждать
спецификации остальных подсистем: после собственных gates он переходит к Stage 9.

Следующий шаг — ограниченный feasibility spike, затем Stages 3–8 только для `VS-1`.

## Stage 3. Requirements и scenarios

- [ ] Присвоить требованиям стабильные `REQ-*` и связать их с `GOAL-*`.
- [ ] Описать основной end-to-end `SCN-*` от профиля до сравнения ветвей.
- [ ] Описать редактирование профиля, выбор, rewind, fork и diff.
- [ ] Описать недостающие, устаревшие и конфликтующие официальные данные.
- [ ] Описать невозможный или финансово неустойчивый сценарий.
- [ ] Описать повторный run и воспроизводимость исторической ветви.
- [ ] Добавить negative, recovery и privacy scenarios.
- [ ] Определить acceptance criterion для каждого требования.
- [ ] Провести анализ противоречий и неоднозначностей.

Выходы: `product/requirements.md`, `product/scenarios.md`.

Exit gate: нет существенного поведения, существующего только в прототипе или устной договорённости.

## Stage 4. Domain specifications

- [ ] Завершить однозначный glossary.
- [ ] Определить entities, value objects, команды, события и состояния.
- [ ] Формализовать стабильный профиль и изменяемые предположения.
- [ ] Формализовать append-only граф Life Git и правила снапшотов.
- [ ] Формализовать типы фактов, provenance и Evidence Passport.
- [ ] Определить детерминированные расчёты, ограничения и неизвестные значения.
- [ ] Зафиксировать `INV-*` для каждого критического перехода.
- [ ] Провести ключевые `SCN-*` по модели от старта до результата.

Выходы: документы в `domain/`.

Exit gate: каждый переход имеет входы, предусловия, результат, ошибки и recovery semantics; LLM не
может обойти доменные ограничения или создать внешний факт без provenance.

## Stage 6. Architecture и contracts

- [ ] Создать system-context diagram и определить компоненты.
- [ ] Зафиксировать dependency direction и границу LLM.
- [ ] Описать data, control и evidence flows.
- [ ] Спроектировать retrieval, immutable snapshots и кэширование.
- [ ] Спроектировать deterministic calculation engine и scenario compiler.
- [ ] Определить схемы профиля, commit, branch, evidence и calculated state.
- [ ] Описать source adapters, timeout, retry, conflict и unavailable semantics.
- [ ] Определить canonical serialization, версии и миграцию.

Выходы: документы в `architecture/`, `contracts/` и начальный набор `ADR-*`.

Exit gate: у каждого компонента есть ответственность, интерфейс, producer/consumer, зависимости и
поведение при ошибке; число внешних интеграций соответствует MVP.

- [ ] Определить privacy model, consent, retention, deletion и export.

- [ ] Описать защиту от prompt injection через источники.

- [ ] Определить производительность канонического демо и режим деградации.

## Stage 8. Evals и validation design

- [ ] Построить `GOAL -> REQ -> SCN -> INV/ADR -> CONTRACT -> TEST/EVAL` matrix.
- [ ] Определить golden profiles и ожидаемые инварианты сценариев.
- [ ] Определить source/provenance conformance tests.
- [ ] Определить проверки воспроизводимости расчётов и ветвей.
- [ ] Создать failure-injection matrix для сети и источников.
- [ ] Определить evals качества пакетов и недопущения галлюцинаций.
- [ ] Создать usability rubric для visual-first результата.
- [ ] Определить installed black-box E2E и отдельную репетицию демо.
- [ ] Сопоставить evidence с шестью критериями конкурса и AI Input/Process/Evals/Output.

Выходы: документы в `evaluation/`.

Exit gate: нет orphan requirements, непроверяемых обещаний или конкурсных тезисов без evidence.

## Stage 9. Baseline и implementation вертикального среза

- [ ] Проверить ссылки, термины, идентификаторы и supersession.
- [ ] Устранить скрытые допущения и двусмысленность.
- [ ] Проверить противоречия между product, domain, UX, architecture и evals.
- [ ] Разделить перегруженные документы.
- [ ] Провести независимое содержательное ревью.
- [ ] Зафиксировать известные ограничения и неизвестные значения.
- [ ] Получить пользовательское подтверждение baseline выбранного вертикального среза.
- [ ] Создать или завершить его change-пакет и implementation tasks.

Exit gate: выбранный срез можно реализовать без изобретения требований, визуальной семантики,
контрактов или критериев готовности во время написания кода.

## Цикл каждого последующего изменения

```text
explore
  -> proposal
  -> requirements + scenarios
  -> clarification
  -> design + ADR
  -> contracts + acceptance/evals
  -> tasks
  -> cross-artifact analysis
  -> user approval
  -> implementation
  -> verification
  -> canonical-spec update
  -> archive change
```
